SCENARIO 01: RUNG 0, DON'T CREATE IT                  script: Stage B (1:30–3:00)

THE IDEA
  The cheapest span is the one you never create. Sampling asks "should I keep
  this telemetry?"; this asks "should I create it at all?". No sampler is
  involved: the spans are never created, so nothing is serialized, sent,
  received or dropped.

  Two picks, both measured on this shop, both one environment variable:

  flagd, the feature-flag service, traces every flag lookup as three spans:
    about 1 in 8 of all spans, and nobody has ever debugged a flag lookup.
    OTEL_TRACES_EXPORTER=none, and flagd stops creating them.
  frontend, one library: Node's http instrumentation. Next.js already records
    every request's server span, so http only adds an identical copy, plus a
    span for every static file (JS chunks, icons). About 1 in 10 spans.
    OTEL_NODE_DISABLED_INSTRUMENTATIONS=http, and they're gone. Traces stay
    connected: Next.js picks up the incoming trace context by itself.

  Together: about 1 in 5 spans the shop creates, gone before they exist.
  The same switch exists per library in every language: Node, Python
  (OTEL_PYTHON_DISABLED_INSTRUMENTATIONS), Java
  (OTEL_INSTRUMENTATION_<NAME>_ENABLED), and .NET.

THE TRADE-OFF (say it)
  If flagd is ever the problem, there are no flagd spans to look at (its
  metrics still flow). The frontend loses its http.server.request.duration
  metric along with the library. Only do this for telemetry you're sure you
  don't need.
